## 2.16 Migration from Monica **[M2]**

A **first-class, guided migration** so a user coming from Monica can bring their data over
with the least possible friction. This is a priority feature — for many users (the author
included) it is the very first thing they will do.

- **Guided wizard**, not a raw import: Settings → Data → *Import people*. The user
  uploads a Monica export; Stella parses it, shows a **preview & mapping summary** (e.g.
  "312 contacts, 540 relationships, 1 208 notes, 87 activities, 96 photos"), lets them
  confirm, then imports inside a single transaction with a progress indicator.
- **Accepted inputs** (support the formats Monica actually offers, in priority order):
  1. **Monica JSON export** (account settings → *Export → JSON*), the richest source.
  2. **Monica SQL dump** (self-hosters’ full export) — parsed read-only into the mapping.
  3. **vCard** (contacts only) as a fallback for partial data.
  The wizard auto-detects the format from the uploaded file.
- **Entity mapping** (Monica → Stella), documented and versioned:
  - Contacts → `contact` (names, nickname, gender, birthdate incl. Monica’s
    unknown-year/age precision → our `birth_date_precision`; deceased flag/date;
    job/company; "how you met" → `how_we_met`/`met_date`).
  - Contact fields (emails, phones, addresses, websites, social) → `contact_field`.
  - Relationships → `relationship`, mapping Monica relationship types to our built-in
    `relationship_type` set, **creating custom types** for anything unmatched
    (cousins, aunts/uncles and nieces/nephews land on the built-ins; `docs/monica-mapping.md`).
  - Notes → `note`; Journal/other free text → notes with a source tag.
  - Activities → `interaction` (kind/date/participants).
  - Important dates / reminders → `important_date`.
  - Tags → `tag`; photos/avatars → `photo` (downloaded/copied into the media volume).
  - Gifts → `gift` records (§2.25.4): idea, given (*offered*) or received; one that cannot be
    a gift (given without a day, an unknown status) stays a labelled note.
  - Life events, pets and other out-of-scope Monica modules → **not lost**: imported as
    structured notes on the contact (clearly labeled), so nothing silently disappears.
- **Idempotent & safe:** dry-run preview first; import is atomic (all-or-nothing) and can
  be run into an empty household; a stable **source id** per record prevents duplicates if
  re-run. Everything imported is attributed to the importing user and **shared**, unless
  the admin picks *private* for this import in the wizard.
- **Report:** after import, a summary of what was imported, skipped, or approximated, with
  any warnings — no silent data loss.
- **Documented mapping table** ships in `docs/` so the transformation is transparent and
  reviewable.

> Implemented as a standalone, well-tested **domain module** (`domain/import/monica`) that
> takes a parsed export and emits Stella entities — pure and unit-testable (test-first),
> with the file upload/UI as a thin edge. See `docs/08-coding-guidelines.md`.

- **Shipped (all three formats):** *Settings → Data → Import people* takes either of Monica's
  exports — the JSON file from *Settings → Export data*, or a `mariadb-dump` of the database —
  plain or gzipped, and works out which it is from the file itself. It then walks three steps: **preview** (counts per
  entity, the custom relationship types it will create, and a "left out, and why" list),
  **import** (one transaction), then **photos** — the admin points the browser's folder
  picker at Monica's `storage/app/public/photos`; each file is matched by name, downscaled
  in the browser like every other upload, and stored, with Monica's avatar choice carried
  over. Everything gets a **stable source id** (`monica:contact:12`), so importing the same
  export twice writes nothing new and the report says so. The mapping table is
  [monica-mapping.md](../monica-mapping.md).

  The **photo step differs by format**, because the formats do: a dump names its files and
  leaves them in Monica's storage folder, so the admin points the picker at it; a JSON export
  carries every picture inside the file, so there is nothing to point at — the server hands
  each one back out and the browser downscales it the same way. Two things the JSON export
  cannot give, and the report says both rather than letting them vanish: Monica does not put
  *"how you met"* or where into that file, and it names a relationship type only in the
  forward direction. And because a source id is Monica's own key, which the two formats spell
  differently (a number against a uuid), importing *both* exports of one Monica into one
  household writes everything twice — pick a format and stay with it.

  **A vCard is read too**, and the wizard is the same for it, with one more step: `.vcf` from
  any address book — a phone, a mail client, Google Contacts, Nextcloud — recognised by its
  `BEGIN:VCARD` line. It carries people and no more: names, nicknames, birthdays, emails,
  phones, websites, addresses, notes, categories (which become tags) and an embedded picture,
  which is stored the same way a JSON export's is. What it cannot carry, and the report says so,
  is how those people are connected — no relationships, interactions or journal entries are read
  from a vCard. Unlike an export of Monica, a vCard is **never imported unreviewed**: between
  preview and import every card is matched against the people already in Stella and answered
  (§2.16.2), so somebody Stella knows is completed instead of coming in twice. A card that comes
  in as a new person keeps a source id of its own (`vcard:contact:<uid>`, or a fingerprint of
  the card when it has no usable `UID`).

### 2.16.1 The import API **[M2]**

For people who arrive as a **list** rather than as an export — a kindergarten class with the
parents, a club roster, a wedding's guests — a script or an assistant can read the list and
send it to Stella in one request, as the member whose token signs it.

**Tokens.** *Settings → API tokens* is every member's, not only the admin's: a token acts as
whoever made it, sees what they see and writes records as theirs, so nobody makes or withdraws
one for anybody else. A token has a name ("Class list import"), a lifetime of 30, 90 or 365
days and a record of when it was last used. It is shown **once**, when it is made — Stella
keeps only its SHA-256, like a session — and starts with `stella_`, so a leaked one is
recognisable. Revoking is immediate and has no undo: a token is withdrawn because it may be in
the wrong hands. A token opens the API and nothing else; under `/api/v1/` the session cookie
is not read at all, so a signed-in browser cannot be steered into calling it by another site.
Tokens are never exported (§2.15).

**Endpoints.** Every request carries `Authorization: Bearer stella_…`; without a live token the
answer is `401` with `{ "error": { "code": "unauthorized" } }`. A `POST` carries
`Content-Type: application/json` — without it SvelteKit takes the body for a cross-site form
submission and refuses it (`403`) before Stella sees it. `?dryRun=` accepts `true` or `false`
and nothing else (`400 invalidDryRun`), so a typo can never mean "write".

| Request | Answer |
|---|---|
| `GET /api/v1/people?q=anna` | `{ people: [{ id, displayName, description }] }` — the household search (§2.9), as the member would see it |
| `GET /api/v1/circles?q=kinder` | `{ circles: [{ id, name, kind, startDate, endDate, memberCount }] }` — name contains the query, ignoring case and accents; all circles without one |
| `POST /api/v1/import` | writes a document (below) |
| `POST /api/v1/import?dryRun=true` | the same answer, and nothing written |

**The document.** People, their contact details, the links between them and the circles they
belong to, in one JSON object. Everything a document *creates* is named by a **ref** it chooses
itself (`[A-Za-z0-9_-]{1,64}`); someone already in Stella is named by id instead, found through
the lookups above.

```json
{
  "source": "kindergarten-2023",
  "visibility": "shared",
  "people": [
    { "ref": "juri", "firstName": "Juri", "lastName": "Example", "birthDate": "2017-10-03",
      "fields": [{ "kind": "address", "value": "Examplestrasse 1, 3007 Bern" }] },
    { "ref": "fabienne", "firstName": "Fabienne", "lastName": "Example",
      "fields": [{ "kind": "phone", "value": "+41 79 000 00 00", "label": "mobile" }],
      "home": { "with": "juri" } },
    { "ref": "leo", "existingId": "01J…",
      "fields": [{ "kind": "address", "value": "Examplestrasse 3, 3007 Bern" }] }
  ],
  "relationships": [{ "from": "fabienne", "to": "juri", "type": "parent_child" }],
  "circles": [
    { "ref": "kg", "name": "Kindergarten 2023/24", "kind": "class",
      "startDate": "2023-08-01", "endDate": "2024-07-31",
      "members": [{ "person": "juri", "role": "Child" }, { "person": "leo", "role": "Child" },
                  { "person": "fabienne", "role": "Parent" }] }
  ]
}
```

- A **new person** has at least one of `displayName`, `firstName`, `lastName`, `nickname`;
  optionally `description`, `birthDate` (`YYYY-MM-DD`, or `--MM-DD` without the year) and
  `fields` (`kind` is one of `phone`, `email`, `address`, `url`, `social`, `date`, `custom`;
  `value`; `label`) and `home`. An **existing person** is `{ ref, existingId }`, optionally
  with `fields` and `home`.
- A **relationship** is `{ from, to, type }` by the type's key — a built-in one
  (`parent_child`, `grandparent_grandchild`, `great_grandparent_great_grandchild`, `sibling`,
  `half_sibling`, `aunt_uncle_niece_nephew`, `cousin`, `parent_in_law_child_in_law`,
  `sibling_in_law`, `partner`, `spouse`, `friend`, `colleague`, `mentor_mentee`, `neighbor`,
  `acquaintance`, `knows`, `other`) or one of the
  household's own (§2.4). `from` is the forward side: for `parent_child`, the parent.
- A **new circle** has a `name`; optionally `kind` (§2.4.2: `friends`, `family`, `school`, `class`, `course`, `club`, `team`, `work`, `neighborhood`, `other`), `description`, `startDate`,
  `endDate`, `parent` — the ref of a circle listed *earlier* in the document, new or existing —
  and `members`. An **existing circle** is `{ ref, existingId }`, optionally with `members` and
  any of the details a new circle has (`name`, `kind`, `description`, `startDate`, `endDate`,
  `parent`), which it is then given — below. A member is `{ person, role, startDate, endDate }`,
  all but `person` optional.
- **Fields complete, never change.** An existing person's `fields` add only what they lack: a
  field whose kind and value (ignoring case and spacing) they already have is left out, and
  everything they have stays as it is — a second, different address is added beside the first,
  because the API cannot tell which one is right. Added fields go after the ones there. Seeing
  the person is enough, as on their page: a way to reach someone is a household fact (§2.2).
- **`home: { with: ref }` moves a person in** with someone else the document names, in place
  of typing their address again — one address for everyone who lives there (§2.2, *A shared
  home*). That person, the holder, must have exactly one address to share: the one home they
  live in, or else their one own address — sent in this document or already theirs — which
  becomes a home they live in too and leaves their fields, as *Also lives here …* does on a
  person page. A holder with no address is `homeNoAddress`, one with two homes or two own
  addresses `homeAmbiguous`: the API cannot tell which is meant. A holder must not live with
  somebody else in turn (`homeChain`), so whose address it is stays plain; nobody lives with
  themselves (`homeSelf`). Someone moving in loses an own address equal to the home's line
  (ignoring case, spaces and punctuation) and keeps a different one — a second address,
  perhaps — and an address field they are sent that equals it is left out like one they
  already have.
- **A circle's details are set when named.** An existing circle takes what its entry names and
  keeps everything it leaves out: a `name` renames it, a `parent` moves it inside that circle,
  and `null` clears what may be empty (`description`, `startDate`, `endDate`, `parent` — a
  circle back at the top); `name` and `kind` cannot be `null`. Unlike a field, a detail
  *replaces* what is there — a circle has one name and one parent — so a dry run lists every
  change, old and new, before anything is written. A value the circle already has is no change,
  which keeps a second sending a no-op; a circle the document created before (`imported`) is
  left alone, details and all. Seeing the circle — and its new parent — is enough, as in its
  edit form (§2.4.2); its visibility is not a detail and never changes. The period is checked
  as a whole, the kept half included: an `endDate` before the `startDate` is refused, for a new
  circle as for an existing one.
- **A circle cannot end up inside itself.** A new parent is checked against the household's
  whole nesting — circles the member cannot see included, answered only as yes or no — and
  against the moves earlier in the document, so `circleCycle` refuses a circle placed inside
  itself or inside a circle nested in it.
- `visibility` applies to every person and circle created; `shared` without it (§2.10).
- Objects are strict: a field Stella does not know is refused, never dropped, so `birthday` for
  `birthDate` is an error rather than a birthday silently lost.

**All or nothing, and every problem at once.** A body that is not a well-formed document is
answered `400` with `{ problems: [{ code: "invalid", path: "people[2].birthDate", message }] }`;
one that is well-formed but cannot be applied to this household is answered `422` with the
problems the planner found — `duplicateRef`, `unknownRef`, `personNotFound`, `circleNotFound`,
`idTaken`, `unknownRelationshipType`, `selfRelationship`, `duplicateRelationship`,
`relationshipContradiction`, `relationshipExcluded` (with the `reason` of §2.4's guardrails and
the `personId` it is about), `duplicateMember`, `circleCycle`, `periodBackwards`, `homeSelf`,
`homeChain`, `homeNoAddress`, `homeAmbiguous`. A circle the
member cannot see, in another household or private to someone else, is `circleNotFound` like
one that does not exist, as a parent too. Either way nothing is written, not even the good
part, and every problem is named, so a script fixes its output in one round. `code` and `path`
are the contract; `message` is an English diagnostic for whoever writes the script.

**Links pass the guardrails.** A link sent through the API meets the same rules as one entered
on a person's page (§2.4): a generation cannot run both ways, a child has at most two parents,
a partnership that still holds stands in the way of another, and so on — read against the
household's record *and* the links earlier in the same document.

**Sending twice changes nothing.** What a document creates is stored under an id made of
`source` and its ref (`api~kindergarten-2023~p~juri`), so a second sending finds it and leaves
it alone; a field, link or membership the person or household already has — under any id — is
left out too, and so is somebody moving into a home they already live in. A home made of a
ref's address is stored the same way (`api~kindergarten-2023~h~juri`). The answer says so
rather than going quiet: each person and circle comes back with a `status` of `new`,
`imported` (sent before) or `existing` (named by id), and `alreadyThere` counts the fields,
links, memberships and residents left out. A field this document added before counts as there
under its id even after its value was corrected by hand, so re-sending never brings the old
spelling back.

**Duplicates are pointed out, never decided.** A name is not an identity — two people can share
one (§2.15) — so the API never concludes that a new person *is* somebody already in the
household. `possibleDuplicates` lists every new person whose name, ignoring case, accents and
word order, somebody the member can see already has, with their ids and birth dates. The way to
act on it is a dry run first, then `existingId` for whoever turns out to be there already.

**The answer** to a successful request, dry run or not:
`{ dryRun, added: { people, fields, relationships, circles, memberships, homes, residents },
changed: { circles },
people: [{ ref, id, displayName, status, fieldsAdded }], circles: [{ ref, id, name, status,
changes }], possibleDuplicates: [{ ref, candidates }], alreadyThere: { fields, relationships,
memberships, residents } }` — `fieldsAdded` is how many fields this sending gives that person,
so a dry run shows who is completed with what; a holder's address that became a home still
counts among theirs. `homes` counts the homes made, `residents` everyone who moved into one,
holders included. A circle's `name` is the one it has after the import, and
`changes` names each detail this sending changes as `{ from, to }` — `{}` when there is none.
For `parent` both sides are `{ id, name }` or `null` (at the top); a former parent the member
cannot see is `{ hidden: true }`. A real import that added or changed anything is written to
the activity log in the member's language ("imported 18 people, added contact details to 3 and
changed 2 circles through the API (kindergarten-2023)" — someone already there who moved into
a home counts among those given contact details), with the visibility of what it imported.

### 2.16.2 Contacts from other address books **[M3]**

People already sit in other address books — Google Contacts, or the Nextcloud the family's
phones sync with — and most of them are already in Stella too. A `.vcf` from any of them goes
through the import wizard's **review** (§2.16): each incoming contact is matched against the
people the importing member may see, the member answers who it is, and only then is anything
written. The answers are remembered, so the same address book can be imported again later and
only what is new or changed is asked about.

**Which address book.** Read from the file itself: a Sabre or Nextcloud `PRODID` is Nextcloud;
a file without `UID`s that carries Google's marks (`X-ABLabel`, the `myContacts` group, a
`googleusercontent` photo) is Google; anything else is *a vCard file*. Google's own groups
`myContacts` and `starred` never become tags.

**Matching.** Candidates are only people the member may see and who are not archived; someone
else's private person is never a candidate, never named and never counted.

| Card | When |
|---|---|
| **Strong match** | it shares an email (ignoring case) or a phone number with exactly one person |
| **Name only** | only the full name agrees, ignoring case, accents and word order, as `possibleDuplicates` does (§2.16.1) |
| **Several people** | more than one person is reached by any rule; nobody is preselected |
| **New** | nobody shares a name, email or phone |
| **Changed** | answered *Same person* before, and the card changed since |

A number is compared as digits with its country (`0041 79 …` is `+41 79 …`). A national
`079 …` has no country and Stella keeps no household country, so it is compared by its last nine
digits: enough to make someone a candidate (*nearly the same phone*), never a strong match.

**The review.** One card per contact, the incoming one beside who it may be, with what *Same
person* would add and what it would not take over. Four answers: **Same person**, **Pick
someone else** (the household search, browsable people only), **New person**, **Skip**. A
strong or changed match starts as *Same person*, and **Confirm all N strong matches** folds them
in one tap; the others start unanswered. The contacts nobody matches are not cards but one
**checklist**, nothing ticked: an address book holds plenty of people the family does not keep,
so the member ticks the ones to add and the others are skipped. *Skip the rest* answers
everything still open. *Import* waits until every contact has an answer.

**What *Same person* writes: missing facts only**, the import API's way (§2.16.1, *Fields
complete, never change*): emails, phones, addresses and websites the person lacks (an address
also compared with the line of a home they live in), birthday, nickname, company and job when
empty, the card's picture when the person has none, and its groups as tags. Labels come along —
*Home*, *Work*, *Mobile*, or Google's own label as typed. A differing **first name, last name or
birthday** is a conflict: both values are shown side by side, Stella's is selected and picking the card's
replaces it. Any other difference is added beside what is there or listed as *not taken over*.

**Applying.** One transaction. Each answer is checked again at write time — a person who became
private or was archived meanwhile is refused and the review shown again, never written to. One
activity-log line for the import, as the member and in their language. A photo that is only a
link (Google's) is not in the file; the review and the result count those.

**Remembered answers** (`contact_source_link`, docs/03) belong to the household. A card
answered *Same person* or *New person* and unchanged since is left out of the next review; a
changed one is shown again with only what is new. **A skip is for good**, even when the card
changes: *Skipped contacts* on the import page lists them with *Ask again*, as *Show declined*
does (§2.4.1). A card's key is its `UID`; Google has none, so its key is the contact id in its
photo URL, else its folded name with its first email or phone — a contact renamed in Google is
new the next time, and matches its person strongly by email or phone.

The linked Nextcloud book (§2.16.3) reviews its new cards the same way.

### 2.16.3 The linked Nextcloud book **[M3]**

The family's phones already sync their contacts with Nextcloud, so Stella links to the
household's **one Nextcloud address book** and the two keep each other up to date. Stella is a
**CardDAV client** of that book, never a server: the phones keep talking to Nextcloud alone.

**Set up by the instance's operator** (docs/07): the book's CardDAV address, a user and an app
password in the environment. Without them the link appears nowhere. The app password stays in
the environment — never in the database, the archive, a log line or a page. The book's cards
remember their answers as `nextcloud:<book>` (`contact_source_link`, §2.16.2).

**When it syncs.** On *Sync now* on the import page, and when a member opens Stella and the last
sync is more than ten minutes old (a minute after a failed one). There is no timer: a household
nobody looks at needs no sync. Opening Stella never waits for it; what it brings shows on the next
page. Each sync asks Nextcloud only for what changed since the last (WebDAV `sync-collection`).
A book out of reach changes nothing and says so on the import page.

**What is kept in step:** first and last name, phones, emails, addresses (a shared home's line
included), birthday and photo. Nothing else on a card is touched, and nothing else in Stella goes
out. Labels go out as *home*, *work* and *cell*; a member's own label goes out as typed. There is
no household country code: a number goes out as Stella holds it.

**In: a changed linked card** is compared with the card as the last sync saw it, so only what
changed on the phone counts. It adds the facts the person lacks, as *Same person* does
(§2.16.2). A card picture fills a person who has none. A changed **first name, last name,
birthday or photo** that Stella holds differently is a **conflict**: it waits under *Data
quality → Nextcloud differences*, any member answers it (*Keep Stella's* or *Take the card's*),
and until then Stella keeps its side and that person's card is not written. A card picture is
taken as it is, without the browser that downscales every other picture (docs/04): one too large
to be its own thumbnail stays on the card.

**In: a new card** — one no answer remembers — waits for the matching review: the import page
shows *N new cards to review*, and the review is §2.16.2's, matched against **shared** people
only, adding people shared and storing card pictures at once. A skip is for good here too.

**In: a card deleted in Nextcloud only unlinks.** The person stays in Stella untouched; a card
for them reappearing later is a new card.

**Out: a change to a linked, shared person** is written to their card at the next sync, the
card's other lines kept as they were. Stella's photo goes out as JPEG — an avatar cropped from
Immich (§2.24) as well. A write that crosses a phone's edit (the card changed meanwhile) is left
for the next sync, which reads the phone's change first.

**Private people never go out.** A private person is never offered in the review; one linked
person who becomes private (a merge can do it) is unlinked at the next sync, before anything is
written. People only in Stella or only in Nextcloud stay where they are unless linked.

**Who did it.** What a sync writes is logged as **Nextcloud**, a system actor: no one who
signs in, never listed among the members (docs/03 §3.1). A conflict answered is logged as the
member who answered.
