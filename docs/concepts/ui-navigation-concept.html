★ Stella · UI Concept

A persistent app shell for Stella

Today the navigation lives only on the dashboard — every sub-page improvises its own back link. This concept replaces that with a persistent shell: a fixed sidebar, a header with a breadcrumb trail and global search, and a bottom tab bar on mobile. Around that, the app becomes relationship-first: people, their connections, where they work, and a household at a glance. The prototype below is clickable.

Starting point

What doesn't work today

Observed straight from the code (src/routes/(app)/): there is no shared layout shell, only a server-side +layout.server.ts.

Dead end

No way back to the dashboard

From a contact, the graph or search there is no link home — only sideways to "Contacts".

Inconsistent

Every page reinvents "back"

Sometimes ← Home, sometimes ← Contacts; the contact list even links to /search. No reliable pattern.

Hidden

Navigation only on the dashboard

Contacts / Circles / Graph live in the dashboard header alone. Everywhere else you have to guess.

Orientation

"Where am I?" goes unanswered

No active marker, no trail. On deeper pages the context is lost.

Guiding ideas

Four principles

Always home

The logo and first breadcrumb take you to the dashboard from any page in one click.

Destinations always visible

A fixed sidebar shows every main area — nothing has to be guessed.

Where am I?

An active marker plus a breadcrumb trail answer the question on every level.

Search & add everywhere

Global search and "Add person" sit fixed in the header — reachable from any context.

Why this split

  • Four fixed tabs + one action. Home, People, Circles, Search cover the whole product; the center plus button creates a person instantly.
  • The title names the place. Together with the active tab it replaces the breadcrumb trail in tight space.
  • Back stays consistent. The contact detail gets a real back arrow; the journal lives inside it and is kept on scroll.
  • Same destinations as desktop. You learn the structure once — it holds on both devices.
Model decisions

Relationships are the core — not circles

From the review: a family is never declared as a group; it emerges from relations between people. That shapes the person page and the add flow.

Relationships on the person

A mini ego-graph plus a list shows everyone directly connected, with their role (mother, brother, partner …).

Add & assign inline

Add a related person, put someone in a circle, or record where they work — all from the person page.

Create several at once

Enter first / last name, then add mother, father, child … via shortcuts or the full type picker. Last name carries over.

A household at a glance

The dashboard leads with metrics — people, relationships, journal entries, circles — each with a 8-week trend.

Supported relationship types

Built-in set shipped with the household. "Other" in the add flow opens a picker over all of these, grouped by category. Non-symmetric types store one row and render the right label per side.

Family

Parent · Child · Grandparent · Grandchild · Sibling · Aunt/Uncle · Niece/Nephew · Cousin · Step-parent · Step-child · Guardian · Godparent · In-law

Romantic

Spouse · Partner · Ex-partner

Social

Friend · Neighbor · Roommate · Acquaintance

Professional

Colleague · Manager · Report · Mentor · Mentee · Teacher · Student · Business partner · Client / Provider

Other

Knows · Connected to (free text on the relationship carries the specifics)

Implementation

From concept to code

Mapped onto the existing SvelteKit structure — all within the golden rules (shell only at the edge, domain untouched).

1

Introduce the shell: src/routes/(app)/+layout.svelte

A shared layout with sidebar + header wraps every app page via {@render children()} — navigation exists exactly once instead of per page.

2

Remove ad-hoc headers from pages

The individual <header>/← Back blocks in contacts, circles, graph, search and contact detail go away. Each page renders only its content.

3

Derive breadcrumbs from the route

A Breadcrumbs component reads $page.route + load data (e.g. the contact name), so the trail is always correct with no per-page upkeep.

4

Mark the active state

The sidebar compares $page.url.pathname against each target and sets aria-current="page" — visible and accessible at once.

5

Dashboard metrics

A load returns four counts (people, relationships, journal entries, circles) + an 8-week series; render as stat tiles with inline-SVG sparklines. Cheap COUNT queries via the access layer.

6

Ego network on the person page

The pure graph core (src/lib/graph/model, buildEgoNetwork) yields direct neighbors; the Cytoscape adapter renders them compactly in the contact detail, plus a list with role labels.

7

Relationship type picker

Load the built-in relationship_type rows (see §3.3); shortcuts map to the common family types, "Other" opens a picker grouped by category.

8

Create several people in one transaction

The create use-case takes a main person plus connected people and writes contacts and relationships in one step (last name pre-filled, role editable per card). Each relationship is stored as a single directional row, so the reciprocal side is automatic — adding Julia as Anna's mother makes Anna show as Julia's child, no second row.

9

Work fields with autocomplete

job_title and company already exist on contact. A tiny +server.ts returns distinct companies for typeahead — no new table.

10

Circles: create-with-members & assign

"New circle" writes the circle + circle_membership rows together; the person page assigns membership inline. Circle field is removed from person-create (family ≠ circle).

11

Journal inline with week pagination

A journal section in the contact detail loads per calendar week (?before=W) and appends on scroll — instead of a separate /journal route.
