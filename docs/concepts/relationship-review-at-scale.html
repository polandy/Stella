A review that stays flat

The household review computes everything — that was decided, against this concept's own earlier advice, in docs/04 §4.9: no cap. What a run finds is what the screen owes you. This concept is the other half of that decision: how a list of 207 claims across 96 people reaches a phone without the page, the payload or the person reading it falling over.

The rule this whole page follows

Nothing is dropped. Everything is folded. A cap removes claims and lies about the total; a fold shows fewer rows and keeps the number honest, with one click to the rest. Every number on the screen below counts the whole household, never the page.

The shape

Three folds, one honest count

Folding happens at three levels, each with its own limit and its own way through. The limits are named constants, not literals scattered across a route and a component.

Fold 1 · the page

10 people at a time

The list is people, not claims, so a person's claims are never split across a page boundary. The pager walks the household in a stable order.

PEOPLE_PER_PAGE = 10

Fold 2 · the group

5 claims per person

One imported company or a sibling group of twelve can carry dozens of claims for a single person. Five are shown; the rest are one link away, on that person's own page.

CLAIMS_PER_GROUP = 5

Fold 3 · the drawer

Declined lives elsewhere

Past a handful, the declined drawer stops being a <details> inside the list and becomes its own paged route. It is history, not work.

DECLINED_INLINE_MAX = 10

Why it is designed this way

Four things the API has to get right

1

The cursor is a person, not an offset

The list shrinks while you answer it. ?after=25 would skip the rows that slid up into the gap. The cursor is the sort key of the last group shown, so answering never hides anything.

2

The totals are computed, the rows are sliced

One run evaluates the whole graph — that is the no-cap decision and it is cheap. What the page limits is the payload: 10 groups × 5 rows, never the count in the header.

3

A fold always names what it hides

34 more for Erika Roth, not show more. A number the reader can check is the difference between folding and quietly truncating.

4

Still no bulk accept

Paging makes a long list workable, which is exactly when a sweep of yes becomes tempting. The answer is still one claim, one decision.

API

What the load returns

The engine is untouched: it still evaluates { kind: 'household-reviewed' } against one view and returns every claim that stands. Paging is a pure function over the grouped result, which keeps it unit-testable without a database and keeps the rule engine the only place that decides what a relationship is. 

// src/lib/suggestions/paging.ts — pure, no deps
export const PEOPLE_PER_PAGE = 10;
export const CLAIMS_PER_GROUP = 5;

/** One page of subject groups, plus the totals for the whole household. */
export interface ReviewPage {
  /** Groups on this page, in the household's stable order. */
  readonly groups: readonly FoldedGroup[];
  /** Open claims across the household — the full count, never the page's. */
  readonly openClaims: number;
  /** People carrying at least one open claim, household-wide. */
  readonly people: number;
  /** 1-based position of this page's first group, for "26–50 of 96". */
  readonly from: number;
  /** Sort key to pass back as `after`, or null on the last page. */
  readonly nextCursor: string | null;
  /** Sort key to pass back as `before`, or null on the first page. */
  readonly previousCursor: string | null;
}

/** A subject's claims, cut to CLAIMS_PER_GROUP with the remainder counted. */
export interface FoldedGroup {
  readonly subjectId: string;
  readonly subjectName: string;
  readonly claims: readonly NamedClaim[];   // at most CLAIMS_PER_GROUP
  readonly totalClaims: number;             // what the rules actually found
}

export function pageOfGroups(
  groups: readonly ClaimGroup[],
  cursor: { after?: string; before?: string }
): ReviewPage;

Build order

What this takes on top of what shipped

  • paging.ts first, as pure functions. pageOfGroups and the group fold take grouped claims and a cursor and return a ReviewPage — no repository, no viewer, no SvelteKit. Its tests are the whole safety net: a cursor that lands on a group answered away, a household smaller than one page, a group of exactly CLAIMS_PER_GROUP, and the property that the pages of a household concatenate back to every group exactly once.
  • A stable sort key. Grouping is by subject today but the order is whatever the engine emitted. Paging needs a total order that does not move between requests — sort name then id, and the id breaks every tie.
  • The route reads the cursor, the engine does not. reviewHousehold keeps returning everything; the load groups, pages and hands the component a ReviewPage. The engine stays the one place that decides what a relationship is.
  • The counters come from the unpaged result, so they are computed before the slice — a regression here is silent, which is why the counting-vs-rendering table above is a contract and not a note.
  • Then the screen, then verification in the running app, then the e2e: a page that answers a claim on page 2 and proves the household count dropped while the page kept its other rows.
Open questions

What this mockup does not decide

  • Is 10 the right page? It started at 25, and rendering the prototype settled it: 25 people came to 44 rows and a 6,115px page — 9.3 phone screens, the same wall the fold is supposed to remove. At 10 it is 17 rows, 2,401px on a laptop and 3.8 phone screens, which is a chore somebody finishes. Both numbers are measured in the prototype at 1280×1000 and 390×844, not estimated. It is still a constant in a pure module, and it should move on the next measurement rather than on a feeling.
  • Does the run need measuring before any of this? Yes, and it still has not been. Folding fixes the page; it does nothing for a rule pass that takes eight seconds. If evaluate over a 2000-person graph turns out slow, that is a separate problem with a separate answer, and this design does not hide it.
  • Should a page remember where you were? The cursor is in the URL, so the back button already works. Storing a "you got to here" marker per member is a different feature — a resumable chore — and it needs a reason beyond convenience before it earns a table.
  • Does search belong here at all? It is the one control that is not folding. It earns its place only if people arrive wanting a specific person; if they arrive wanting to work the list down, it is clutter. Worth watching rather than deciding now.
  • What about a person with 300 claims? Fold 2 sends them to a page that then has the original problem. The same pager applies there, but the rule producing 300 claims about one person is the actual bug, and the number on screen is what makes it visible.
