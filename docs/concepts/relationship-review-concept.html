One review for the whole household

The per-person review shipped in #110: a member opens a profile, presses Check relationships, and answers what the rules find. This concept adds the step that is still missing — one run over everyone, and a screen that collects what came back. The rows, the answers and the dismissal log are the shipped ones, unchanged.

Built — this is what shipped

Shipped: the person-reviewed trigger, three answers per row (accept / decline / leave), suggestion_dismissal keyed by the claim rather than the rule, the declined drawer with Offer again, and KinSuggestions.svelte as the one row component for both the Also true? block and the review panel. Drawn here and then built on the same branch: the household-wide pass at Settings → Check relationships, on the household-reviewed trigger. The built screen follows this drawing except where noted below.

Why a batch

Nobody opens 186 profiles

A per-person review only reaches the people someone thinks to check, and the households that need it most are exactly the ones with years of imported links nobody has looked at. The rule set is pure and runs against a view the viewer may see, so asking it about everyone is the same work, done once, in one place.

1

The claim, not the person

A batch reaches the same claim from both ends — Lisa's review and Hans's raise it alike. The list is deduplicated on (relation, pairKey), the key the dismissal log already uses, so it appears once.

2

Three answers, still

Accept stores the link through the checked action, Decline writes the dismissal, and leaving a row alone stays free — the rule that keeps a long list honest.

3

No bulk accept, least of all here

A screen with 40 rows is precisely where a sweep of yes would be offered and precisely where it must not be.

4

Form actions, no JavaScript needed

Run is a POST; each answer is its own form, like the shipped panel. The progress bar is an enhancement over a request that works without it.

Prototype · click it

Settings → Check all relationships

The entry sits in Settings beside Export and Import: it is household work, not a person-page action. Press Check all relationships, then answer the claims — accept, decline, undo, and open the drawer to put a declined one back.

Build order

What this would take, given #110

  • A household trigger in the engine. { kind: 'household-reviewed' }, or a use-case that walks every visible person through the existing person-reviewed path and deduplicates on (relation, pairKey) — the engine stays pure either way, and the dedup is a pure function with its own test.
  • One view, not 186. buildView already takes the whole visible kinship graph; a household run builds it once and evaluates against it, so the cost is one read plus the rules, not a query per person.
  • The screen. /settings/relationships reusing KinSuggestions.svelte under a per-person heading, with the same three form actions pointing at the settings route instead of the contact route.
  • Unit tests first for the trigger, the dedup and the visibility property (a claim naming a person the viewer cannot see never reaches the list), then the edge, then — after sign-off in the running app — the e2e. The per-person panel is still waiting for its own e2e, so the batch should not overtake it.
Open questions

What the mockup does not decide

  • Does a run get stored? The screen above stores only decisions and recomputes the claims on each visit; last check is then a timestamp. A stored result set would let two members work the same list without it shifting — worth it only if that actually happens.
  • How long does one run take? Unmeasured. If a real household makes it slow, the honest fix is paging the run, not a background job with its own state to explain. Measure before designing for it.
  • Certain-only in a first pass? L1 and L2 are both certain, so today the question is moot — but a batch is exactly where a likely rule like L3 would produce dozens of rows and invite fast tapping. Worth deciding before L3 lands, not after.
  • Does the entry point belong in Settings? It is where Export and Import live, and it is also where members rarely go. A prompt after an import, when a graph full of unreviewed links has just arrived, would reach them at the one moment it matters.
  • Answered, not open: a decline does not expire (§6.5), the log is household-scoped, and it travels with the export — all settled in #110.
