Concept · Relationships (docs/02 §2.4)

Several people, one link

Today the relationship form takes one person. To record that Lio is the child of Anna and Bert, the household fills the form, saves, opens it again and enters the whole thing a second time. This concept lets the person field take several people. The type, the status and the save are shared, and each pair still becomes its own relationship. Stella already knows when the second parent is likely, so it offers that person inside the form, before anything is saved.

Decisions

What the design settles

D1 · Same form, same picker

The person field takes chips

There is no new screen and no "add several" mode to find. PersonSearchSelect already has multiple + keepSearch (circle members, moment people), so the relationship form turns it on. Typing a surname keeps listing the family, and Add all N matching works as it does in circles.

D2 · The type decides how many

Caps come from the rules, not the UI

Partner / spouse stays one person (one partnership at a time, §2.4). Child of allows two parents minus the ones already on record, so with Anna on file it stops after one more, and the field says so in place of the input. All other types (parent of, sibling, grandparent, godparent, friend, colleague…) have no cap.

D3 · Refused per person, never dropped

The reason sits on the chip

Today a picked person greys out the type entries they rule out. With several people, the person who causes the refusal is marked instead: the chip turns red and the reason appears under the field ("Otto Meier: already Parent of Anna"). Add stays off until that chip is removed. Stella never saves the valid ones and quietly skips the rest. A type entry is only greyed out when it is refused for every picked person. With one person that is exactly today's behaviour.

D4 · The second parent, offered in the form

One tap, never preselected

Once a parent is picked for Child of, Stella checks rule L3 (docs/02 §2.4.1): exactly one current partner, a partnership that did not begin after the child's birth, and a free parent slot. If all hold, it offers that partner under the field: "Also Bert Brunner? Anna's partner". The offer only becomes a link if someone taps it, so suggestions stay opt-in. The same function can later give L3 to the Also true? block.

D5 · Shared vs. per pair

Status is shared, the since date is per pair

Status: one select, stands on current. Since: the birthday rule is worked out per pair. If every pair gets the same day (both parents → the child's birthday), it is one field, as today. If the days differ (several children), the field lists the day for each person and offers Use one date for all. How they connect: one field labelled for all 2. Each link keeps its own text, editable on its row afterwards.

D6 · One command, all or nothing

One save, one undo, one outbox entry

A new command relationship.addMany writes every link in one transaction. The guards check the graph and also the other links in the same batch, so two new parents for a child who already has one are refused, even when each would pass on its own. The toast reads "2 links saved · Undo", and Undo takes both back. Offline it is one queued item: "Lio · Child of Anna Brunner and Bert Brunner".

D7 · After saving

Also true? for the whole batch

The card comes back with the Also true? block worked out from all new links. Lio's sister Mia is offered Anna and Bert as parents in one list (L1), not two lists after two saves. A row with several claims gets an Add all (scenario 4). Each claim is still shown and still sent on its own.

D8 · New people still work inline

Create a person as one more chip

When nobody matches, the picker's create option adds a chip, as it does today. The suggested description reads from Lio's side: "Parent of Lio Brunner". Several new people in one go each get their own chip and their own quick-add.

Building it

Shape of the change

Domain first and test-first, per docs/08. The domain gets one new use-case, which loops over the existing single-link guards and adds the check across links in the same batch.

// src/lib/commands/commands.ts: queued commands stay readable, so `relationship.add` is kept
'relationship.addMany': {
  contactId: string;
  typeChoice: string;               // the same "type:side" the select posts today
  status: RelationshipStatus;
  description: string | null;       // copied onto each link
  links: { targetId: string; sinceDate: string | null }[];   // ≥ 1, distinct, per-pair since
}

// src/lib/server/domain/relationships/add-many.ts — deps: { repository, clock, idGenerator }
addRelationships(deps, actor, payload) → Result<Relationship[], RelationshipRefusal[]>
//   every link checked against graph + earlier links of the batch; any refusal → nothing written

// src/lib/suggestions/rules/links.ts — pure, reused by the form (D4) and later by Also true?
likelyCoParent(graph, parentId, childId) → ContactId | null   // rule L3 / L3b
  1. PR 1 — domain + wire. addRelationships use-case, cross-batch guards (third parent, duplicate in the batch), the relationship.addMany command and dispatcher, the ?/addRelationships action. The single form keeps working unchanged.
  2. PR 2 — the form. Multi picker, cap per type (D2), refusal per chip (D3), shared vs. per-pair fields (D5), one toast and one undo, Also true? for the batch (D7). docs/02 §2.4 + using-stella.md, both languages.
  3. PR 3 — the second parent. L3 as a pure rule with its step-parent check, the offer in the form (D4), and Add all on a group in Also true? and the reviews.
For the owner

Decided

The owner settled all three open questions on 2 October 2026, each as recommended.

Q1 · decided

Second parent: offered, never preselected

One tap on "Also Bert Brunner?" turns him into a chip. Nothing is in the form that nobody picked, so a step-parent cannot slip through as a parent.

Q2 · decided

"How they connect": one field for all

Labelled for all N, copied onto each link, editable per row afterwards.

Q3 · decided

Add all in Also true?: PR 3

It ships with L3, so PR 1 and PR 2 stay small.
