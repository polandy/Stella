Which Thomas: namesakes in the @-picker

Picking one of two Thomas in the @-picker inserts @Thomas, and nothing else remembers which one was meant. On save the server finds two people for the handle and leaves it as text: the mention is lost, silently. This page walks through the fix: say which one in the list, remember the pick instead of guessing from the name, and ask when there was no pick.

What happens today

Today

Three identical rows. Picking the second one writes @Thomas. The line under the field names a Thomas, the last one in the list. The server's resolver sees a collision (mentions.ts, createHandleResolver) and keeps the text. A moment with only this mention is refused as “needs a mention”. A note or journal entry saves, but without the mention.

Editing an entry turns every stored token back into @Name (bodyForEditing). Saving an entry that mentions a namesake drops that mention too.

Proposed

Every Thomas gets the second line ⌘K already shows. The field keeps the readable @Thomas and remembers which Thomas was picked at that place. On save, the browser writes the id token itself, the form the server already takes as it is. A handle nobody picked that could mean two people is refused with the candidates named, and the text stays in the field.

The household below has three people called Thomas, a Thomas Lang, and the two Brunners. Type @th, pick one with the arrow keys and Enter, keep typing before and after the pick, and save. The panels under the composer show what the field remembers and what would be stored.

      The rules

      The handle in the textOn saveWhy
      Picked in the listThe picked person's id token, whatever the nameThe pick is the author's answer; the name is only what is shown.
      Typed, one person has itThat person, as todayNothing to ask.
      Typed, several people have itRefused, naming each with their second line; the text staysA mention lost without a word is only noticed months later, on an empty page.
      Typed, nobody has itStays text, as today@home or somebody's handle elsewhere is often not a mention at all.
      Reopened for editingShown as @Name, remembered as the stored idEditing must not lose what saving kept.

      The same rules apply in all three places an @-picker lives: the moment composer, the note field and the journal (MentionTextarea). They apply to a moment kept on the device too, which then carries id tokens and has nothing left to guess when it is sent.

      How it is cut

      • Two pure functions in src/lib/mentions/, test-first: toEditable(body, nameOf) → { text, picks } and toStored(text, picks) → body, plus shiftPicks(before, after, picks), which carries picks across an edit (common prefix and suffix; a pick the change touches is dropped).
      • The second line is tellApart and NamesakeLine, as in ⌘K. The mention candidates gain description, metPlace and metDate.
      • The server changes in one place. createHandleResolver already knows a handle is ambiguous. It now says so instead of answering null, and resolveMentions reports ambiguous handles. The moment, note and journal use-cases refuse with a translatable phrase that names the candidates.
      • Without JavaScript, the form posts the text as before. A namesake handle is then refused with the reason, never dropped.
      • Not in scope: chips inside the field (a rewrite that would cost the plain-textarea fallback), and a suffix in the handle like @Thomas2 (it would stay in the stored text).

      Recommendation: build parts 1–3 together. The second line and remembering the pick fix the path people actually take. The refusal closes the rest, so no mention disappears without a word.
