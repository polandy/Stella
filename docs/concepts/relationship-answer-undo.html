Answering without losing your place

Found on the family instance, not in a test: accepting a suggestion throws the page back to the top. The list keeps the right page — that part was fixed — but an answer is still a form post and a redirect, so the browser reloads and the scroll goes to zero. This is the other half: answer in place, leave gracefully, and offer the way back for a few seconds.

What the test missed, and why

The e2e asserts that the URL still carries q= after an answer. That is the proxy for the promise, not the promise: it proves which page you are on, never where on it you are. A case that scrolled down, answered, and asserted the scroll offset had not moved would have caught this on the first run. That case is part of this change.

Three faults, three fixes

What goes wrong now

Now

The page jumps to the top

Every answer is a POST followed by a 303. The browser throws away the rendered document and scrolls to zero, so on row forty you lose your place on every single answer.

Instead: the answer never navigates. The form is enhanced, the row is settled on the spot, and nothing else on the page moves.

Now

The row just vanishes

It is there, then it is not, and everything below snaps up by its height — which is also how the next row ends up under a thumb that was aiming at something else.

Instead: the row marks itself answered, holds for a moment, then collapses its own height over 260ms so the list closes rather than snaps.

Now

A mis-tap is permanent

Accept writes the link immediately. Taking it back means finding the person and deleting the relationship by hand — and on a declined claim, digging through the log.

Instead: eight seconds of Undo. The request does not go out until the window closes, so undo costs nothing and writes nothing.

Prototype · click it

Accept a row and watch the page hold still

Scroll down inside the frame first, then accept or decline something — the frame must not move. Two variants of where Undo lives; switch between them and see which one you want. The counter at the top drops the moment a row is answered and comes back if you undo it, because a number that waits for the window to close would be describing a list nobody is looking at.

Suggestions

The frame scrolls on its own. If accepting a row moves it, the change has failed.

What it reuses

The machinery already exists, and is already tested

Stella has held removals back behind an undo window since the journal work: a store with an injected timer, a toast region, and the rule that the request is not sent when the button is pressed. Nothing here is a second mechanism — a suggestion answered is a row leaving a list with something to do when the window closes, which is exactly what that store already models.

How it talks to the server

Not a new endpoint — the form action already is one

Nothing here needs a hand-written AJAX route. A SvelteKit form action is already the endpoint; use:enhance intercepts the submit, posts to that same action with fetch, and Svelte patches the rows that changed. With JavaScript off the very same form posts normally. One code path, two behaviours — which is why every other screen in Stella already does this and KinSuggestions.svelte is the one that does not.

LevelWhat crosses the wire per answerWhat it costs
Today

Enhanced

Held
enhance + the undo window		 Nothing for eight seconds, then one POST Scroll kept, the row and the counters update locally, and an undo costs no request at all. No re-evaluation until the reader pages or leaves.

The middle row is the trap. It looks like the obvious fix and it does solve the jump — but it re-runs the rules over every visible person for each claim answered, and how long that takes on a real imported household has never been measured (it is still an open question in the scale concept). The held version sidesteps the question rather than answering it: the screen already knows what it just did, so it has nothing to ask the server for.

The window

What happens in those eight seconds

MomentOn screenOn the server

Page left first—flush() sends everything still pending before the navigation completes
The POST failsthe row comes back with the error on it — a contradiction (409) is a real answer, not a glitchnothing was written

Pausing on hover matters more than it sounds. The classic failure of an undo window is reaching for it as it expires. Pausing while the pointer is on the control, or while it has keyboard focus, costs one line and removes that whole class of frustration.

Without JavaScript

The screen still works, and still lands near you

Every control here stays a form. With JavaScript off there is no window and no undo — the answer posts and the page reloads, as today. What changes is where it lands: the redirect carries the answered claim's anchor, so the browser restores the position it was at instead of the top. A declined claim is still recoverable from the log; an accepted one from the person's own page. That is a worse experience, honestly stated, rather than a broken one.

Motion

How the row leaves

  • Collapse, not fade-out. The row animates grid-template-rows: 1fr → 0fr on its own wrapper, which animates height without anyone measuring a pixel and takes the gap with it. 260ms on the standard ease — long enough to read as closing, short enough not to be waited on.
  • The colour says which answer it was before it goes: a green wash for accepted, a red one for declined. That is the only moment the two answers look different.
  • Nothing below moves early. The height comes out during the collapse, so the list closes over the gap instead of snapping up.
  • Reduced motion means no motion. Under prefers-reduced-motion the row changes colour, holds the window, then is simply gone — the undo is the point, the animation is not.

Open questions

What this mockup does not decide

  • Toast or in-place? The toast is what Stella already does for removals and keeps one undo language across the app. The in-place strip is where the eye already is, which matters on a long list where the toast sits far from the row you just answered. Switch between them in the prototype above — this is the one decision the mockup is asking for.
  • Is eight seconds right here? It is UNDO_WINDOW_MS, shared with journal removals. Answering suggestions is faster work than removing entries, so several rows can be in flight at once — the toast region stacks them, but four countdowns at once may read as clutter. Worth watching on the real instance before tuning.
  • Should accepting really be reversible by holding it back? Holding means the link is not written for eight seconds, so a second member looking at the same moment does not see it yet. The alternative — write immediately and delete on undo — is worse: it leaves a real relationship in the household's history for the length of a mis-tap.
  • What about the person page? The same rows appear in the Also true? block and in a profile's own review. The behaviour should be identical there, since it is the same component — but that block is short, so the jump nobody noticed there is the same bug.
