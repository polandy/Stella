## 4.3 Application structure

A conventional SvelteKit layout with a clear server/domain separation. The tree is the folder
level of `find src -type d`; tests sit beside their file. *Pure* marks a folder that may not
import `$app`, `$env` or `@sveltejs/kit` (docs/08 §8.2 item 18); a `*.svelte.ts` beside pure
code is its browser adapter. The words used here are defined in docs/03 §3.0.

Client code is sliced by feature: each folder under `lib/` is one context (`people/`,
`stream/`, `circles/`, …) or one cross-cutting concern (`ui/`, `design/`, `i18n/`, `motion/`,
`pwa/`, `graph/`). A new module joins the folder of the context it serves rather than starting
a folder of its own; `components/` mirrors the split, `ui/` for the design system.

**Principles:**

- **Ports & Adapters.** The domain owns narrow interfaces (ports); `db/` and other
  infrastructure implement them (adapters); use-cases receive their collaborators
  (repository, `Clock`, `IdGenerator`) via an explicit `deps` argument. A **repository** is an
  aggregate's write side and the one-record reads its writes rest on (`ContactRepository`); what a
  screen lists is a **read model** of its own (`ContactDirectoryReads`, `ContactNameReads`), so a
  use-case takes only the narrow port it reads and a test fakes only that. One adapter per port:
  `adapter-ports.test.ts` refuses an infrastructure factory declared to return `A & B`;
  `lib/server/services/` is the composition root, the only module that wires concretes. It
  builds one `AppServices` per process, grouped by bounded context (`auth`, `people`, `relationships`, `circles`, `media`, `story`, `notes`, `records`, `household`, `archive`, `immich` (null without a configured Immich), `release` and `offline`
  (the dispatcher, its handler table in `lib/server/commands/handlers.ts`)), and `hooks.server.ts` hands it
  to every request as `locals.services` — a route reads `locals.services.auth.sessionDeps`,
  and a test can hand a route an `AppServices` over fakes. Only edge code imports the module
  — the SvelteKit edge itself (routes, `hooks.server.ts`); the actions several pages share
  live with them under `routes/(app)/_shared/` and take the slices they reach as arguments.
  A type-only import of a slice is open to anyone who asks for narrow deps;
  `services/boundary.test.ts` and the ESLint import rule refuse every value import from
  outside the edge, deep paths into the folder (`../services/app-services`) included. Pure logic takes no dependencies. Full convention:
  [`08-coding-guidelines.md` §8.3](../08-coding-guidelines.md).
- All data access goes through `lib/server/domain/*`, which calls `lib/server/access`
  for every read/write. **No route or component queries the DB directly.** ACL rules
  (§3.7) live in exactly one place.
- SvelteKit **form actions** for mutations (progressive enhancement, works without JS);
  **`+server.ts`** endpoints for JSON needs (graph data, search-as-you-type, uploads).
- **Load functions** are server-side and already visibility-scoped.
